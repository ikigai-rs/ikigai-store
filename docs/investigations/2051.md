# Shared nesting check migration: blocked by unchanged tests

Ledger #2051, reproduced 2026-10-22 against ikigai-rdf 0.2.7.
The migration is **not implemented**. Production code and existing tests remain unchanged.
The item requires stopping if the shared checker reads an existing test differently.

The store does duplicate the pre-parse scanners in `src/depth.rs`.
Before the experiment, these commands passed:

```sh
cargo test --features rdf-12 --lib depth::tests
cargo test --features rdf-12 --test triple_term_nesting --test triple_term_growth
```

Results: 13/13 unit tests and 11/11 integration tests passed.

Applying `2051-candidate.patch` replaces the scanners with the requested dispatcher,
uses `ikigai-rdf = "0.2.7"`, aliases the constant, and uses the shared Turtle check
for serialized stored terms. No tests were edited. Running the unit-test command
then produced 11 passes and two failures (full output in `2051-depth-test.log`):

- `nesting_after_a_string_or_iri_is_still_counted`: N-Triples input
  `<urn:a> <urn:q> 'x . <urn:a> <urn:p> {over} . # '` with `{over}` a
  65-level triple term is admitted by the shared Turtle scanner. The unchanged
  test requires refusal. Turtle treats the single-quoted region as a string.
- `rdfxml_that_is_not_utf8_is_refused`: little-endian UTF-16 bytes for `<r/>`
  are admitted by the shared XML checker. The unchanged test requires refusal.

`rdfxml_counts_parse_type_triple_elements` passes unchanged, including its
200-level `parseType=Resource` case; the 0.2.7 fix is present. The stored-term
boundary test also passes. Further migration testing stopped at these differences.

The quoted expectations anticipated these two differences and proposed editing the
tests. That conflicts with the pinned task's explicit unchanged-test/stop requirement;
this investigation follows that requirement and does not edit the tests.

Load-path review: `limits::check_load` propagates the first `for_slice` parse error
before asking the writer to load anything. `LoadEndpoint::invoke` subsequently uses
`load_from_reader` and propagates its error. A search of `src` found no `bulk_loader`
or `on_parse_error` use. This is a code review finding, not an additional runtime
experiment with the two admitted documents.

CI on this documentation-only PR validates the unchanged store, not a successful
migration. The candidate patch and failing log are retained as reproduction evidence.
